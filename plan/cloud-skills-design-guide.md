## 一、Skills 到底是什么？先讲个故事

### 1.1 一句话定义

**Skill 就是一份给 AI Agent 看的"操作手册"**——里面有说明书（`SKILL.md`）、可能有脚本、模板、示例数据，
Agent 在执行任务时把它读进来，就知道"这类活该怎么干"。

举例：

```text
incident-response/          ← 一个 Skill（事故响应手册）
├── SKILL.md                ← 说明书：name、description + 正文
├── checklists/             ← 配套文件
│   └── triage.md
└── scripts/
    └── collect-logs.sh     ← 脚本（注意：导入阶段只当"字节"，绝不执行）
```

### 1.2 没有 Skills 时会怎样？

Agent 的"技能"散落在每个人的本地磁盘、聊天记录、个人笔记里：

- **无法共享**：同事写好的好手册，你拿不到；
- **无法版本化**：改了三次之后，没人知道上周跑出来的是哪一版；
- **无法重现**：今天跑出来的结果，明天用"同名但已改过"的手册再跑，结果不一样；
- **无法授权**：谁可以用哪本手册，说不清；
- **无法审计**：谁在什么时候上传了什么内容，查不到。

所以我们要把 Skill 变成**云端一等公民**：有归属、有版本、有授权、有审计、可重现。

### 1.3 整个设计要解决的核心矛盾

> **内容必须永远不变（可重现），名字和配置必须可以变（好管理）。**

这两件事听起来矛盾，实际上必须同时成立。整套设计的绝大部分复杂度，都来自这一条。
解决思路是**把"身份"和"内容"拆成两个东西**：

| | 名字/身份 | 内容 |
|---|---|---|
| 例子 | 图书馆的"书目条目" | 某一版印刷的书 |
| 可以改吗 | 可以（改名、下架、换简介） | 永远不可以（改内容 = 出一版新的） |
| 对应概念 | **Skill** | **SkillRevision** |

## 二、全局地图：先看大图，再钻细节

### 2.1 参与的角色

```text
 用户 / 前端看板
      │ ①上传（zip/tar）、配置 Agent 默认用哪些技能、发起执行
      ▼
 ┌──────────────────────────────────────────────┐
 │  Cloud（控制面 + 业务权威）                    │
 │  · PostgreSQL：技能元数据、版本记录、导入日志   │
 │  · 授权、幂等、快照、签发取回凭证               │
 └───────┬──────────────────────────┬───────────┘
         │ ②执行描述符（含 Skill 引用） │ ③签发短期取回凭证
         ▼                          │
   Controller（只中转，不代理字节）    │
         │                          │
         ▼                          ▼
      Node ────④直连下载─────────────────► Object Storage
   （缓存、投影、准备就绪）                （唯一保存包字节的地方）
         │
         ▼
      Agent 进程（真正干活的 AI）
```

### 2.2 两条平面必须分开（这是理解全案的关键）

| | 控制面 | 数据面 |
|---|---|---|
| 传什么 | "这次执行要用哪个技能的哪一版" | 手册的**实际字节**（几百 KB ~ 几百 MB） |
| 走哪条路 | Cloud → Controller → Node | **Node → Object Storage 直连** |
| 为什么 | 身份/授权信息小、要可审计 | 大流量不能压垮协调层，也不能让 Node 长期持有仓库钥匙 |

一句话记忆：

> **控制面送"清单"，数据面送"货物"，Controller 只递清单不搬货。**

### 2.3 一次完整的旅程（时间线）

| 步骤 | 发生在哪 | 干什么 |
|---|---|---|
| 1 | 前端 → Cloud | 上传 zip/tar，Cloud 归一化、校验、算指纹 |
| 2 | Cloud | 写"入库单"（TX #1）→ 存字节到 Object Storage → 验证 → 落库建版本（TX #2） |
| 3 | 用户 | 在 Agent 上勾选"这个 Agent 默认用哪些技能" |
| 4 | Cloud | 发起执行：把勾选的技能**冻结**成一次执行的快照 |
| 5 | Cloud → Controller → Node | 下发执行描述符（含技能清单和短期取回凭证） |
| 6 | Node → Object Storage | 直连下载字节，校验指纹，存进本地缓存 |
| 7 | Node | 把缓存内容"投影"成 Agent 能读的文件树，全部就绪后标记 READY |
| 8 | Node | READY 之后才启动 Agent 进程，Agent 开始干活 |

## 三、十个核心概念（先背下来，看文档不迷路）

沿用"图书馆"比喻：

| 概念 | 图书馆里的对应物 | 一句话解释 |
|---|---|---|
| **Collaboration Workspace** | 一个分馆 | 技能的归属与授权边界（注意：**不是**运行时 workspace） |
| **Skill** | 书目条目 | 可变的业务身份：有名字、简介、归属；可以改名、可以下架 |
| **SkillRevision** | 某一版印刷的书 | 不可变的内容身份：一旦创建，内容永不改变 |
| **canonical tree** | 规范化后的书稿 | 把任何来源（目录/zip/tar）归一化成的同一棵文件树 |
| **content_digest** | 书稿内容的指纹 | 对规范化文件树算出的 SHA-256，回答"这份内容是什么" |
| **package_digest** | 装订成册后整包的指纹 | 对最终容器字节算出的 SHA-256，回答"这包字节是什么" |
| **SkillIngestion** | 入库单 / 物流跟踪单 | 一次导入的持久化日志（saga journal），崩溃后靠它恢复 |
| **AgentSkillBinding** | 某人的常用书单 | Agent 的可变配置："我以后默认用这几本" |
| **ExecutionSkillBinding** | 一次借阅的清单 | 不可变的执行事实："这次任务用了这几本的这几版" |
| **Execution / Attempt** | 一次讲座 / 讲座的第 N 次排练 | 逻辑执行 / 物理尝试；重试 = 同一讲座再排练一次 |
| **VerifiedSkillBundle** | 分馆的备货仓库 | Node 上"已验证"的字节缓存 |
| **ExecutionSkillProjection** | 讲台上摆的那一套书 | 每个 Attempt 专属的、Agent 实际读到的文件树 |
| **RetrievalCapability** | 一次性的提货码 | Cloud 签发的短期只读取回凭证（不是长期仓库钥匙） |

### 3.1 三个最容易混的"identity"

```text
business identity    SkillRevision.id            → "这是哪个 Skill 的第几次内容提交"
content identity     (sha256, content_digest)    → "这份内容是什么"（跨 Skill 相同）
physical identity    object key                  → "这包字节在仓库里放哪"（跨 Skill/空间相同）
```

**为什么要分三层？** 因为三种"相同"含义不同：

- 两个不同的 Skill 可以有**完全相同**的内容 → 业务上必须是两个独立资源，但物理上可以只存一份；
- 同一个 Skill 反复上传同一份内容 → 业务上只该有一条版本记录，物理上也只该有一个对象；
- 内容变了 → 一定是新版本、新对象。

## 四、主线一：让字节永远可复现（canonical package v1）

### 4.1 问题：为什么不直接对上传的 zip 算 hash？

```text
同一个文件夹，今天打包一次 zip，明天再打一次 zip：
  · mtime 不同        → 字节不同
  · 压缩级别不同       → 字节不同
  · 文件在压缩包里的顺序不同 → 字节不同
  · 操作系统不同（Windows/macOS）→ 字节不同
```

如果拿 zip 的 hash 当"内容身份"，同一份内容会被当成无数份不同内容——去重失效、缓存失效、
"同一内容必然同一结果"这个承诺直接破产。

### 4.2 解法：先把输入归一化，再确定性编码

```text
directory ┐
zip       ├─► ① 归一化为 canonical virtual tree（相同路径 + 相同字节）
tar       ┘        │
                   ├─► ② 编码为 ManifestV1（清单）
                   │
                   ├─► ③ content_digest = SHA256("ora-skill-tree-v1" ‖ 0x00 ‖ ManifestV1)
                   │
                   └─► ④ 拼装成 ora-skill-package v1 容器 → package_digest = SHA256(整包字节)
```

关键点：**归一化时不改写用户文件**。不改 markdown、不重排 YAML、不换行、不注入字段、不"帮你美化"。
只定义"文件树长什么样、怎么编码"，不动"作者写了什么"。

### 4.3 清单（ManifestV1）的精确布局

没有 JSON、没有 protobuf，就是一段固定的大端序二进制：

| 字段 | 宽度 | 说明 |
|---|---|---|
| `manifest_version` | 2 字节 | 固定 `1` |
| `file_count` | 4 字节 | 文件数（至少 1，必须含 `SKILL.md`） |
| 每个文件：`path_length` | 4 字节 | 路径字节长度 |
| 每个文件：`path` | 变长 | 规范相对路径（POSIX 风格，`/` 分隔） |
| 每个文件：`file_size` | 8 字节 | 字节数 |
| 每个文件：`file_sha256` | 32 字节 | **原始二进制**（不是十六进制字符串） |

为什么用这种"长度前缀 + 固定字段序"而不是 JSON？因为**任何实现都只能写出同一种字节**——
没有字段顺序、空格、map 顺序、可选字段这些"自由发挥"的空间。

### 4.4 tree digest 的推导（注意 domain separation）

```text
content_digest = SHA256( ASCII("ora-skill-tree-v1") ‖ 0x00 ‖ ManifestV1_bytes )
                         └────── 领域分隔串（16 字节）──────┘
```

加这个前缀干嘛？防止"对清单的裸 hash"和"对其他东西的 hash"在推导上可以互换——
让这个哈希**只可能是**这个用途，杜绝未来歧义。

### 4.5 容器（ora-skill-package v1）的布局

```text
偏移 0x00   magic           8 字节   "ORASKILL"（人类可读的格式界线）
偏移 0x08   package_version 2 字节   固定 1
偏移 0x0A   manifest_length 8 字节   清单长度
偏移 0x12   manifest        变长      完整的 ManifestV1
之后        file bodies     变长      按清单顺序逐个拼接的原始文件字节
```

v1 **不压缩**。压缩属于传输/存储层的事，一旦进内容身份，不同压缩级别就会产生不同字节，
可复现性就没了。

### 4.6 路径规则：只拒绝，不"帮忙清理"

合法路径必须是：相对路径、不以 `/` 结尾、无 NUL、无 `.`/`..`/空分量、只用 `/` 分隔符。

**非法路径一律拒绝**，绝不静默改写：

```text
a/../b   → 拒绝（不改成 b）
./a      → 拒绝（不改成 a）
a//b     → 拒绝（不改成 a/b）
/abs     → 拒绝（不去掉开头的 /）
C:\x     → 拒绝（不转成 C:/x）
```

Windows 的反斜杠可以在**入口边界**统一映射成 `/`，但映射之后必须重新做一遍完整校验。
另外：**存储的路径字节原样保留**（不做大小写转换、不做 Unicode 归一化），
但要检测"大小写不敏感冲突"（`Foo.md` 与 `foo.md` 同时存在 → 拒绝），
因为这样的包在 macOS/Windows 上会出问题。

### 4.7 资源上限（防止一个包打爆服务器）

| 限制 | 默认值 |
|---|---|
| 单 Skill 最大文件数 | 4096 |
| 单文件最大字节 | 256 MiB |
| 全部文件合计 | 1 GiB |
| 单条路径最大字节 | 1024 |
| 单个路径分段 | 255 字节 |
| 清单最大字节 | 8 MiB |
| `SKILL.md` 最大字节 | 1 MiB |
| 整包最大字节 | 1 GiB + 16 MiB |
| 上传压缩包请求体（产品冻结上限） | 256 MiB |

这些是"库级默认值"，超限的候选直接失败，**不创建任何版本记录**。

## 五、主线二：把手册收进系统（导入）

### 5.1 三种输入，一条管线

| 输入 | 说明 |
|---|---|
| `directory` | 服务器能访问的本地目录（CLI / 服务端内部用） |
| `zip` | 上传的 ZIP 字节 |
| `tar` | 上传的**未压缩** TAR 字节（`tgz`/`tar.gz` V1 不支持） |

公开 HTTP 接口只接受 `zip` / `tar`（客户端有本地目录，先打包再传）。
压缩包类型由客户端**显式声明**（`source_kind=zip|tar`），
**绝不**根据文件名后缀猜、不靠 MIME 嗅探、不"ZIP 解不开就试 TAR"。

### 5.2 递归发现：一个 `SKILL.md` 就是一个技能

```text
上传的包/
├── README.md                    ← 游离文件：忽略（但必须先过安全检查）
├── incident-response/           ← 一个候选技能根
│   ├── SKILL.md                 ← 它的直接父目录就是"候选根"
│   └── scripts/collect.sh
└── web-design/                  ← 另一个候选技能根
    └── SKILL.md
```

规则：

- 递归找 `SKILL.md`，**每个 `SKILL.md` 的直接父目录 = 一个候选技能根**，其子树属于这个技能；
- 候选根之外的文件（游离文件）**忽略**，但仍然要先通过安全检查——不能因为"反正要忽略"就跳过校验；
- **嵌套根非法**：如果一个候选的子树里又出现 `SKILL.md`，**整个 source 直接失败**
  （不猜测谁属于谁、不合并、不拍平）；
- **同一次 source 内出现两个同名技能**（派生出的 `canonical_name` 相同）→ **整个 source 失败**，
  不搞先到先得、不靠数据库唯一索引兜底决定业务语义。

为什么这两种情况要"整包失败"而不是"跳过坏的那个"？因为它们属于**结构歧义**：
外层和内层的文件归属无法在不引入新规则的情况下确定。此时正确做法是让用户改包，而不是系统猜。

### 5.3 `SKILL.md` 的元数据契约

`SKILL.md` 开头是一段由 `---` 包裹的 YAML frontmatter：

```markdown
---
name: incident-response
description: 处理线上事故的标准流程
---

# 正文……
```

| 规则 | 内容 |
|---|---|
| `name` | **必填**，必须是字符串，trim 后匹配 `[A-Za-z0-9._-]+`，不以 `.` 开头，≤ 200 字节 |
| `description` | 可选，trim 后 ≤ 4096 字节 |
| 缺失 `name` | **失败**——不退回目录名、不退回压缩包文件名 |
| `name: 123` | **失败**——不做"帮你转成字符串" |
| 重复 key / 非法 YAML | **失败**（确定性失败，不是"最后一条生效"） |
| 未知字段与正文 | 原样保留，不解析、不校验、不重写 |

**`canonical_name = ASCII lowercase(name)`**，这是从内容字节到"技能标识"的**唯一**变换：

- 不做 slugify（multica 的 `[^a-z0-9]+ → -` 会把 `my.skill` 和 `my-skill` 压成同一个名字，
  直接违反唯一性要求）；
- 不做 Unicode 归一化（字符集本来就是纯 ASCII）；
- 只小写。所以 `Review` 与 `review` 会被视为同一个技能名。

**为什么 `canonical_name` 必须只从内容派生？** 因为它是幂等身份和匹配键的一部分。
如果它还能依赖目录名，那么"同一个压缩包解压到不同目录"就会产生不同身份，
幂等和恢复立刻失去确定性。

### 5.4 失败分三层（小白最容易混的点）

| 层级 | 例子 | 结果 |
|---|---|---|
| **source 结构失败** | 压缩包损坏、路径穿越、不支持的特殊文件、嵌套根、同包内重名、没有任何候选 | **整个请求失败**（400），一条导入日志都不产生 |
| **候选准备失败** | 某个 `SKILL.md` 元数据非法（没有 name、类型不对……） | 只有**这一个**候选失败（响应里单独列出），其他候选继续 |
| **候选业务失败** | 授权失败、幂等冲突、对象存储写入失败、激活冲突 | 进入"批次部分成功"语义，逐项报告 |

### 5.5 批次 = 部分成功（这是刻意的）

```text
发现候选 → 逐个校验 → 各自独立导入 → 汇总报告
                        ↑
              一个失败，不回滚其他成功的
```

响应里汇总 `created / updated / unchanged / failed`。
**绝不允许**把整个批次包进一个数据库事务里——那是"一个坏包毁掉 99 个好包"的做法。

### 5.6 不做重命名猜测

如果用户上传的内容里 `name` 变了，系统**不会**去猜"这是不是原来那个技能改的名"：

- 批量导入：只按 `(空间, canonical_name)` 匹配，同名 = 同一个技能，不同名 = 新技能；
- 显式更新：由接口参数 `target_skill_id` 指定"更新哪一个"，`name` 变了也不改判；
- **不做**任何基于目录路径、描述相似度、字节相似度、显示名的启发式关联。

为什么？因为猜测必然有猜错的时候，而猜错的后果是**把 A 的内容写进 B 的历史**——
这种错误无法被审计发现，比"多建一个技能"严重得多。

## 六、主线三：导入事务（saga / journal-first）

### 6.1 故事：上传到一半崩了怎么办？

一个包可能有几百 MB，上传/入库过程中可能遇到：网络超时、进程被杀、对象存储抽风。
如果用"一个数据库事务包住全部"，事务会被外部调用拖到超时，锁长期占用，而且**数据库事务无法回滚
已经写进对象存储的字节**——跨系统的"分布式事务"是个陷阱。

### 6.2 解法：三段式 + 先写"意图"

```text
【事务外】准备（纯 CPU）
   归一化 → 算 content_digest / package_digest → 推出 object key

【DB TX #1】（短、只碰数据库）
   鉴权 → 绑定 Idempotency-Key → 插入入库单
   state = 'planned'，记下 object_locator、expected_digest、请求指纹
   COMMIT                    ← 关键：先落"意图"和稳定身份

【事务外】外部阶段
   PutImmutable(对象) → 必要时 probe 对账 → 三重验证
                          （状态推进到 storing / verified）

【DB TX #2】（短、只碰数据库）
   创建/复用 SkillRevision → finalize 入库单 → CAS 切换 current_revision_id
   COMMIT
```

**为什么 TX #1 必须排在写对象之前？** 因为崩溃之后要能"对账"。
如果先写了对象再记数据库，崩溃后你连"我本来要往哪个 key 写什么"都不知道，
只能靠猜——而猜是不允许的。

### 6.3 对象键（object key）是内容的纯函数

```text
object_key = "skills/ora-skill-package/v1/sha256/<package_digest_hex>"
例：          skills/ora-skill-package/v1/sha256/3f0c…e1a9
```

它**不含**任何业务身份：没有租户、没有空间、没有技能 ID、没有上传者、没有时间戳、没有随机数。

这一条同时送了三份大礼：

1. **物理去重自动成立**：相同内容必然算出同一个 key，不需要任何去重表；
2. **崩溃恢复有落点**：key 是确定的，所以能按它去问"对象在不在、对不对"；
3. **写路径和读路径不会跑偏**：读取侧只能消费这个 key 规则，不能自己发明一套。

### 6.4 外部结果的五种分类（不是 `err != nil` 二选一）

| 分类 | 含义 |
|---|---|
| `CONFIRMED_PRESENT_MATCHING` | 对象存在，且通过全部三条验证 |
| `CONFIRMED_ABSENT` | 外部明确回答"不存在" |
| `MISMATCH` | 对象存在，但和期望不符（长度/包指纹/树指纹任一不符） |
| `DEFINITE_FAILURE` | 能证明请求没被受理（DNS 失败、连接被拒、429、参数/大小被拒） |
| `INDETERMINATE` | 无法判定（超时、响应丢失、连接后才断、5xx、请求发出后被取消） |

三条判"不确定"的原则：

- **无法确定时选 `INDETERMINATE`**。把"可能已经写成功"误判成"没写成功"，会导致盲目重写，
  掩盖真正的不一致；反过来最多多一次无害的探查；
- **`err != nil` 不能作为"可以安全重试"的依据**——Go 的 error 表达不了"远端可能已经提交"；
- **任何应答（包括"写入成功"）都不等于验证**。进程可能在收到应答前就被杀了，
  所以"我们发出去的是什么"不能证明"外部现在是什么"。

### 6.5 验证三条（缺一不可）

```text
① SHA256(取回的字节) == package_digest      ← 字节级：就是那些字节
② skillpkg.Decode(取回的字节) 成功           ← 结构级：magic/版本/边界/排序/路径/每个文件的 hash/恰好读完
③ 解码出的 tree digest == content_digest     ← 内容级：就是那棵树
```

第 ③ 条是决定性的：因为包字节是文件树的确定性函数，"能解码且重算出的树指纹等于期望值"
就等价于"这棵树就是期望的内容"，**完全不需要信任对象存储的任何字段**。

注意 ①③ 覆盖不同的失效模式：①抓字节损坏/替换，③抓"合法但不是期望的那份内容"。
所以即使 ① 过了，③ 也**必须**独立执行。

### 6.6 MISMATCH 必须 fail closed（绝不"修好它"）

如果 key 上有一个对象，但内容对不上：

- **禁止**覆盖它；
- **禁止**先删再写；
- **禁止**"反正长度一样就用它"；
- **禁止**换个 key 绕开。

允许的动作只有：导入标记为 `failed`（稳定错误码 `object_identity_mismatch`），
保留证据等人工处理，**不创建版本记录、不动当前指针**。

理由：一个"放在内容寻址的 key 上、却不匹配这个 key"的对象，
只可能来自存储端损坏、写 key 的 bug、或外部干预。
"修好它"会销毁唯一能说明发生了什么证据，还可能把错误内容永久登记成某技能的当前版本。

### 6.7 崩溃恢复表

| 崩在哪 | 外部世界 | 恢复动作 |
|---|---|---|
| TX #1 之后、写对象之前 | 对象不存在 | 探查 → 不存在 → 用**重建的**字节写入 |
| 写入进行中（结果未知） | 不确定 | 探查 → 五分类，**绝不在没探查前重写** |
| 写完之后、TX #2 之前 | 对象已正确存在 | 探查 → 匹配 → **直接认领（adopt）**，不重写 |
| TX #2 内部 | 数据库原子性负责 | 幂等重放：命中唯一约束则复用既有版本 |
| TX #2 之后 | 已一致 | 无需外部动作，激活结果按落库结果重放 |

"外部已存在但数据库还不知道"是**正常状态**，要认领，而不是当冲突——
这正是"先记录意图、对象不可变且内容寻址"带来的好处。

### 6.8 字节从哪来？——client-driven continuation

一个诚实且重要的设计选择：**V1 服务端不保存包字节，也不自动恢复**。

- 崩溃后，客户端用**同一个 `Idempotency-Key` + 逐字节相同的 source** 重新提交；
- 服务端重新归一化 → 重建出完全相同的字节和身份 → 命中原来那条入库单 → 对照请求指纹确认是"同一请求" → 继续；
- 因为编码是确定性的，"重建"和"当初那份字节"在正确性上等价。

所以状态是被明确区分开的：

```text
durable state recovery   = 从数据库恢复：身份、状态、幂等身份、激活结果   → V1 提供
durable payload recovery = 从服务端恢复包字节                            → V1 不提供（靠重建）
```

如果客户端再也不重提交，那条入库单会**无限期停在 `planned`/`storing`**——
这是**合法状态**，不自动清理、也不假装服务端能自己推进。运维可以列出这些"搁浅"的记录人工处理。

### 6.9 幂等"三兄弟"：三个不同概念，谁也别代替谁

| 概念 | 作用域 | 规则 |
|---|---|---|
| `Idempotency-Key` | 请求级 | 同 key + 同请求语义 → 重放；同 key + 不同语义 → 409 冲突 |
| content dedup（内容去重） | Skill 级 | `UNIQUE(skill_id, 算法, content_digest)` → 复用同一条版本记录 |
| physical dedup（物理去重） | 对象级 | key 由字节推导 → 相同字节全世界只有一个对象 |

推论：不同 key 导入同一份内容 → 多条导入日志，但收敛到**同一条版本记录 + 同一个物理对象**；
不同 Skill 导入同一份内容 → **两条独立版本记录**，但**共享同一个物理对象**。

### 6.10 请求指纹：为什么"同一请求"不能只看内容

```text
request_fingerprint = 确定性编码(target_skill_id, display_name, summary,
                                content_digest, package_digest) 再取 SHA-256
```

因为**同一份内容可以服务于不同业务请求**：导入到 A 技能 和 导入到 B 技能 是两件事；
带不同显示名/摘要也是两件事。只看内容就会把"不同请求"误判成"同一请求"，
从而返回错误的缓存结果。

而 `Idempotency-Key`、`canonical_name`、`workspace_id` 不进指纹——它们已经构成
**幂等命名空间**（用来"找到那条既有记录"），指纹是**相等判定键**（用来"判断这次请求是不是同一件事"）。
定位键 vs 判定键，职责不同。

排除在指纹之外的（因为这些在归一化时就已丢弃）：multipart boundary、压缩包内 entry 顺序、
压缩元数据、mtime/uid/gid、HTTP header 顺序、传输文件名。

### 6.11 激活 = 乐观锁 CAS，冲突要"持久化地记住"

把一条版本设为"当前版本"是可变业务状态，用 `Skill.version` 做乐观并发：

```sql
UPDATE skills SET current_revision_id = <rev>, version = version + 1
WHERE id = <skill> AND version = <expected>
```

如果并发冲突（CAS 失败）：

- 这条版本**依然合法存在**（将来还能被激活），**不能**丢失；
- 当前指针**不能**被陈旧写入覆盖；
- 导入状态仍然推进到 `committed`；
- 结果**持久化**记在 `activation_outcome`（`activated` / `activation_conflict`），
  **不依赖那次 HTTP 响应的内存状态**。

重放时直接读这个落库值返回，**不再重试 CAS**。想真正重试激活？用**新的 `Idempotency-Key`** 发起新请求。

### 6.12 入库单的状态机

```text
planned   ──► storing ──► verified ──► committed
（已记意图）  （待对账）   （已验证）    （已落库，含激活结果）
                  │
                  └────────► failed（只表达确定性永久失败）
```

要点：

- **不确定永不记为 `failed`**：`storing` 才是"待对账"的家；
- `verified` **等价于**"三条验证全过"，"写入成功"和"已存在"都**不足以**进入 `verified`；
- `committed` 必须真的存在版本记录行；
- 状态推进用条件更新（`WHERE state = 期望值`）做栅栏，不新增 version 列。

### 6.13 公开上传接口速览

```text
POST /api/v1/tenants/:tid/spaces/:spaceId/skills/imports
Header: Idempotency-Key（必填，≤200 字节）
Body:   multipart/form-data
        · source_kind = "zip" | "tar"（必填，显式）
        · source      = 压缩包字节（单个 part）
        · target_skill_id?（显式更新目标）
        · display_name? / summary?（caller 业务元数据）
```

- 需要空间的 **owner/admin** 权限；非成员一律 404（不泄漏存在性）；
- 客户端**禁止**传 `canonical_name` / `content_digest` / `package_digest` / `object_locator` / `revision_id`
  ——这些必须由服务端从字节派生；
- 响应是 200 envelope：`{ sourceKind, preparationFailures[], ingestions[] }`；
  只有结构性失败才 400；
- 部分成功也是 200：单个候选失败、甚至激活冲突，都不改变整体状态码。

## 七、主线四：执行快照与重试语义

### 7.1 可变的配置 vs 不可变的执行事实

```text
AgentSkillBinding（可变）        "这个 Agent 以后默认用这几本手册"
        │  只在创建 Execution 时被读取一次
        ▼
ExecutionSkillBinding（不可变）  "这次执行用了这几本手册的这几版"（含精确 digest）
```

**执行创建那一刻就把技能冻结**。之后：

- 改 Agent 的默认技能配置 → 只影响**未来**的执行；
- 把某个技能切到新版本 → 只影响**未来**的执行；
- 软删某个技能 → 已经在跑/已完成的执行快照**不受影响**；
- Node **不允许**自己去查"当前版本是哪个"，Controller **不允许**重新解析技能配置。

### 7.2 为什么必须冻结？

因为"可重现"的前提是"输入确定"。如果执行过程中输入还可能变，
那么"昨天同样的任务跑出不同结果"就无法解释，retry 也失去意义。

### 7.3 Execution 与 Attempt：重试 ≠ 再跑一次

```text
Execution（一次逻辑执行，输入不可变）
├── Attempt 1   ← 物理尝试，失败
├── Attempt 2   ← retry：同一个 Execution，同一份输入，重新尝试
└── ...
```

| | Retry（重试） | Run Again（再跑一次） |
|---|---|---|
| 是什么 | 同一个 Execution 下**新增一个 Attempt** | **创建一个新的 Execution** |
| 技能输入 | **原样复用**同一份快照 | **重新解析**当前的 Agent 配置与技能版本 |
| 适用 | 网络抖动、节点故障等 | 用户明确想"用最新配置再跑一遍" |

三种失败要分开：**执行输入永久性失败**（输入本身有问题）、**临时取回失败**（可重试）、
**节点本地失败**（磁盘满了之类，不代表输入有问题）。

另外：**V1 不做"文件级续传"**。失败的 Attempt 绝不原地复活，
中间产物（staging）一律当作可丢弃，重试时从"已验证缓存"重新构建。

## 八、主线五：把技能送到 Node（本章是上一轮问题的完整版）

### 8.1 控制面送清单

Node 收到的每个技能是一份**描述符**，不是包：

```text
SkillBundleRef
├─ skill_revision_id     ← 不可变内容身份
├─ content_digest        ← 校验用的完整性锚点
├─ size_bytes
├─ package_format / version
└─ retrieval             ← 一次性的取回凭证
```

### 8.2 数据面直连：Node → Object Storage

- **Controller 不代理包字节**，Cloud API 也不是"下载通道"；
- 数据面是 Node 直连对象存储；
- 因此 Node 不需要长期仓库凭证——它拿的是一次性的**取回凭证（RetrievalCapability）**。

### 8.3 取回凭证的三条铁律

1. **它本身是秘密**（bearer credential）：短期有效、只读、只针对那一个不可变对象、
   没有列举/写入/删除权限。完整 URL **绝不**落库、落日志、进错误、进 fixture；
2. **续签不许改身份**：过期后用 `(execution_id, attempt_id, skill_revision_id)` 三元组续签，
   服务端校验"这个 Attempt 属于这个 Execution、这个 Execution 确实绑定了这个版本、Attempt 还有资格"，
   然后**只为同一个版本**重新签发。绝不查"当前版本"、绝不重解 Agent 配置；
3. **丢了能重来**：Cloud/Controller 重启后，凭数据库里的绑定关系重新签发即可，
   **不需要**恢复旧凭证——这正是"凭证不持久化"能成立的原因。

另一个常见混淆点：**授权 ≠ 完整性**。HTTP 200、凭证有效，也**不能**说明内容正确；
Node 必须自己按 `content_digest` 独立校验。

### 8.4 Node 本地缓存（verified cache）

缓存的身份是 **`算法 + content_digest`**，与业务归属无关：

```text
命中  → 校验证据 → 直接用已验证字节
未命中 → 取凭证 → 下载到临时区 → 校验大小 → 校验指纹 → 原子发布进缓存
```

性质：

- **先验证，后发布**：错误大小/指纹的东西永远进不了缓存；
- **并发安全**：多个 Attempt 同时要同一份内容，最终只产生一个完整可验证的条目，
  读者要么看到"没有"，要么看到"完整"，**永远看不到写了一半的**；
- **不可变**：发布后不再改；
- **可弃**：整个缓存删掉，后果只是"重新下载"，云端业务状态毫无影响；
- **有界**：必须有容量/回收策略，不允许无限增长。

### 8.5 per-Attempt 投影 + 就绪屏障

缓存里的字节还不是 Agent 能用的形态，需要最后一层"投影"：

```text
VerifiedSkillBundle → AgentRuntimeAdapter（按各 Agent 的原生目录约定摆放）
                    → 每个 Attempt 自己的一份文件树（ExecutionSkillProjection）
                    → staging 写完 → 校验 → 原子发布 → READY
```

- **Agent 绝不直接读写共享缓存**（禁止可写硬链接这类会污染缓存的玩法），
  投影只能是复制/reflink/只读挂载等保缓存不变的方式；
- **半成品永不可见**：先在临时区写完再原子发布；
- **READY 是硬闸门**：所有必需技能都已解析、已验证、已发布、运行配置已准备，
  才允许进入启动；**任何一个必需技能失败 → 准备失败 → Agent 不启动**。
  没有"降级成警告继续跑"这个选项（V1 也没有"可选技能"这一说）；
- **重试不恢复半成品**：新 Attempt 重新构建，可以复用缓存里已验证的字节，但不继承旧的中间状态；
- **不认识的文件要保留**：清理只删除"能证明是自己拥有的"路径；
- **同一 Agent 原生路径冲突时 fail closed**：两个技能要投影到同一个原生路径 → 准备失败，不覆盖；
- **物化过程不执行任何技能内容**（脚本、二进制、WASM 在这一路全程只是字节）；
- **READY 不代表任何沙箱隔离**——当前 Node 没有通用的安全沙箱，文档和证据都不得暗示有。

## 九、这样设计的好处（重点）

### 9.1 可重现性：同样的输入，永远同样的结果

| 机制 | 好处 |
|---|---|
| 执行创建时冻结精确版本 | 事后改配置/换版本都不影响已发出的执行 |
| 内容身份只由规范文件树决定 | 目录/zip/tar 三种来源算出同一个指纹 |
| 规范化不改写用户文件 | 跑出来的内容就是作者写的那份，不掺系统加工 |

**如果不这样做**：同一个任务今天跑和明天跑结果不同，且无法解释差在哪——调试和审计都做不了。

### 9.2 省存储、省带宽：三种"去重"自动生效

- 相同内容在不同技能间**只存一份物理对象**（key 由内容推导，物理去重是免费的）；
- 同一内容反复导入**只产生一条版本记录**；
- Node 上同一份内容**只下载一次**，跨 Attempt、跨技能复用缓存。

**好处**：存储成本、下载流量、冷启动时间同时下降，而且**不需要任何额外的去重服务或去重表**。

### 9.3 安全：默认不信任任何人

| 设计 | 挡住的风险 |
|---|---|
| Node 只拿短期一次性凭证 | 长期凭证泄漏、越权访问整个仓库 |
| 凭证不落库/不落日志 | 一次日志收集就把全公司的仓库钥匙收走 |
| 授权只在 Cloud、从服务端归属推导 | 伪造 tenant/workspace 参数越权 |
| 跨空间一律 404 | 通过错误码差异探测别人的资源是否存在 |
| 路径 reject 不 clean | 路径穿越写出到预期目录之外 |
| 物化过程不执行内容 | 上传一个包就等于在服务器上执行代码 |
| MISMATCH fail closed | 把被篡改/损坏的内容永久登记为"当前版本" |
| 不假装有沙箱 | 给出根本不存在隔离的安全承诺 |

### 9.4 恢复简单：只做"重建"，不做"续传"

- 外部写入永远先记意图（journal-first），崩溃后有据可查；
- 恢复只依据**持久化身份 + 外部探查**，不依据内存进度、日志、"通常会发生什么"；
- 已经正确存在的对象直接认领，不重复写；
- 失败 Attempt 的中间产物一律丢弃重建，而不是小心翼翼地"续上"。

**好处**：恢复逻辑可以做得**简单且可测试**——简单的东西才不容易出错。
文件级续传听起来高级，实际上是 bug 的温床。

### 9.5 演进友好：换供应商、加格式都不动业务

- 对象键不含供应商、bucket、region；换对象存储不改任何落库记录；
- 端口（port）只有三个操作语义，没有 List/Delete/Copy/Presign；
- 包格式带版本号，未来 v2 与 v1 字节即使碰巧相同也不会互相覆盖；
- Agent 各自的目录约定被隔离在 `AgentRuntimeAdapter` 里，云端的技能模型不认识任何具体 Agent 的路径。

**好处**：今天选的存储商不是终身绑定；以后支持新的技能来源（Git、URL、运行时快照）
可以复用同一条规范化管线。

### 9.6 确定性：把"自由发挥"的空间全部封死

| 做法 | 目的 |
|---|---|
| 清单用固定字段序的二进制，不用 JSON | 任何实现只能写出同一种字节 |
| 树指纹加领域前缀 | 哈希用途不可互换，杜绝歧义 |
| 压缩包类型显式声明 | 不靠猜测，不靠 fallback |
| 重名、嵌套、非法路径一律拒绝 | 系统不替用户做有歧义的决定 |
| 不做重命名推断 | 宁可多建一个技能，也不把内容写错历史 |

**好处**：任何两个实现（云端和节点、生产与测试）对同一输入必然得出同一结论。

### 9.7 边界清晰：每个角色的职责写死

```text
Cloud      → 业务权威、授权、快照、签发凭证
Controller → 只中转，不鉴权、不持久化凭证、不搬字节
Node       → 只信任已鉴权的不可变描述符，独立校验内容、缓存、投影、就绪门控
Object Storage → 只保存不可变字节，不承担授权
```

**好处**：出问题时能立刻定位"这是谁的责任"；加新角色时不会把授权悄悄扩散出去。

### 9.8 成本可控：明确说了"不做什么"

- 服务端不保存包字节（数据库只存元数据和指向）→ 数据库不会被几百 MB 的包撑爆；
- 不做分布式事务 → 不需要跨系统两阶段提交；
- 不做后台恢复 worker → 不需要第二套持久化和 GC；
- 不做压缩 → 不引入压缩级别导致的不确定性。

**好处**：每一处"少做"都换来一个可验证、可测试、可解释的系统。

## 十、刻意不做的事（V1 非目标）

| 不做 | 为什么 |
|---|---|
| 全局技能（不属于任何空间） | 归属与授权必须唯一明确 |
| 个人技能 / 执行时临时增删技能 | V1 只用 Agent 的持久默认配置，语义简单 |
| 更新时把技能移动到别的空间 | 移动 = 复制/导出/导入，产生新资源 |
| 嵌套技能包 | 文件归属有歧义，直接拒绝 |
| 符号链接等特殊文件 | 会在物化时逃逸投影目录 |
| 导入/物化时执行技能脚本 | 上传不该等于远程执行代码 |
| 通用 Node 安全沙箱 | 需要独立架构决策，不能靠 READY 假装 |
| 文件级断点续传 | 恢复复杂度爆炸，收益低 |
| 可变的 SkillRevision | 内容身份一旦确定就不能变 |
| Node 自己解析"当前版本" | 输入必须由 Cloud 冻结 |
| Controller 代理包字节 | 数据面与控制面必须分离 |
| 长期的存储凭证进业务消息 | 凭证纪律 |
| 自动 GC / 删除对象 | 需要先冻结"哪些引用必须保留" |

## 十一、小白 FAQ（最容易卡住的十个问题）

**Q1：为什么 Skill 和 SkillRevision 要分成两个东西？**
因为"可改的"和"不可改的"必须分开。名字、简介、归属要能改；内容一旦确定就不能变，
否则"同一次执行用了哪一版"就无法回答。分开之后，改名字不动内容，改内容必然出新版本。

**Q2：为什么改个名字有那么多规则？**
因为 `canonical_name` 不只是给人看的——它是幂等身份和匹配键的一部分，必须**只从内容字节派生**。
一旦允许"从目录名猜"或"自动 slug 化"，同一份内容在不同环境下就会得到不同身份，
去重、幂等、恢复全部失效。

**Q3：为什么不能直接拿 zip 的 MD5 当内容指纹？**
因为 zip 里含 mtime、压缩级别、entry 顺序等噪声，同一份内容打包两次就不同。
正确做法是先把内容归一化成文件树，再对清单算指纹。

**Q4：为什么"上传成功"还不算"验证成功"？**
因为"我们发出了一次写入"不等于"外部现在就是这些字节"——进程可能在收到应答前就崩了。
所以任何应答都只是线索，必须**实际取回字节并独立校验**才算数。

**Q5：为什么服务端不自己恢复上传中断？**
因为 V1 服务端不保存包字节（那是对象存储的职责），也没有后台恢复进程。
正确路径是客户端用同一个幂等键重提交，服务端**确定性地重建**出一模一样的字节——
因为编码是纯函数，"重建"和"原来那份"等价。

**Q6：为什么 Node 要自己缓存，不每次下载？**
下载慢、费流量。缓存的键是内容指纹，所以跨执行、跨技能都能复用；
而且缓存是可弃的——删掉只会重新下载，不会丢任何业务数据。

**Q7：retry 和"再跑一次"有什么区别？**
retry 是同一个执行（同一份冻结输入）再试一次；再跑一次是新建执行，会重新读取当前配置。
混在一起会导致"我以为在重试，其实输入已经变了"。

**Q8：为什么 READY 不叫"沙箱就绪"？**
因为当前 Node 没有通用的安全隔离能力。READY 只表示"输入齐了、可以启动了"，
把它说成安全隔离就是给出不存在的承诺。

**Q9：为什么删技能不删对象？**
因为删除是业务动作，而对象可能还被别的技能共享、或被未完成的执行引用。
先软删（业务上不可见），对象回收需要独立决策，先冻结"哪些引用必须保留"。

**Q10：为什么需要两个指纹（content_digest / package_digest）？**
它们回答不同问题：树指纹回答"内容是什么"（决定业务去重、缓存键），
包指纹回答"这包字节是什么"（决定对象键、字节级损坏检测）。
一个包字节合法、包指纹正确，内容仍可能是**另一棵树**——所以两个都要。
